# nova-duckdb

DuckDB для Nova: настоящие типы колонок, Appender для массовой записи и расширения
`core_functions` и `icu`, влинкованные статически, — во время работы пакет никуда не
ходит по сети.

**Это не полная привязка DuckDB.** Версия 0.1 отдаёт из Nova законченное ядро и то,
что нужно первому потребителю; остальное добавляется минорными версиями по мере
появления потребителей и **без пересборки библиотеки** — статический архив уже
содержит всё. Запрос на расширение — задача с указанием потребителя и функции, а не
«на всякий случай».

**Тег — несущий, как бы ни называлась версия.** Потребитель подключает
пакет через `version = "0.1"`, а резолвер берёт самый свежий подходящий **тег** —
значит фикс, лежащий на `main`, не доходит ни до кого, пока не оттегирован,
а следующий тег сдвигает сборку каждого потребителя — без объявления и без
единого действия с его стороны. 0.1.0 релизом не объявлен — и всё равно
работает как релиз для того, кто от него зависит.

## 0.2.1: DuckDB и nova-tls в одной программе

**0.2.0 вместе с nova-tls непригоден, берите 0.2.1.** Тег `v0.2.0` не тронут.

DuckDB несёт свою копию mbedTLS (3.6.4), nova-tls — свою (3.6.2), с разной
конфигурацией и потому с разной раскладкой структур. Обе экспортировали одни и те же
237 функций `mbedtls_*`. В программе с обеими компоновщик либо отказывал (дубли
символов), либо при другом порядке связывал обе копии с одним определением, и открытие
базы С КЛЮЧОМ портило кучу (`0xC0000374`, замер в claude-limits 2026-09-30). Без ключа
ничего не падало, поэтому 0.2.0 прошёл собственные тесты.

0.2.1 собирает DuckDB с принудительно подключённым `native/duckdb_mbedtls_prefix.h`
(`CMAKE_CXX_FLAGS` в обоих сборочных скриптах), и все эти имена становятся
`nova_ddb_mbedtls_*`. Держат это две проверки:

* `scripts/check-mbedtls-prefix.py` читает собранные архивы и падает на любом внешнем
  имени `mbedtls_*`, определённом или упомянутом, — и на полном отсутствии имён с
  префиксом: это значило бы, что заголовок до компилятора не дошёл;
* `scripts/run-with-tls.py` собирает и запускает `examples/03-with-tls` (ключ, запись
  2000 строк, повторное открытие и чтение, разбор корней TLS до и после). В цикл
  стражей CI не входит — Linux CI пока не умеет компоновать C++, — поэтому
  запускается перед каждым тегом.

В Nova-интерфейсе ничего не меняется. Потребитель один раз пересобирает DuckDB:
заголовок префикса входит в ключ кэша сборки, старые архивы не подхватятся.

## Как пользоваться

```nova
import duckdb.{Database, DbOptions, DuckError}
import duckdb.types.{Value}

fn main() Io -> () {
    with Fail[DuckError] = |e| { print("duckdb: ${e.message()}") } {
        consume db = Database.open("limits.duckdb", DbOptions.defaults()) {
            consume con = db.connect() {
                ro _ = con.exec("CREATE TABLE sample (at TIMESTAMP, percent TINYINT)")

                // Appender — единственный быстрый путь внутрь: построчный INSERT
                // стоит около двух миллисекунд, а сто тысяч строк через Appender —
                // около десяти миллисекунд суммарно.
                consume app = con.appender("", "sample") {
                    app.row([Value.Instant(now), Value.Int(74)])
                    app.flush()
                }

                consume r = con.query("SELECT count(*) FROM sample") {
                    print("строк: ${r.value(0, 0)}")
                }
            }
        }
    }
}
```

Каждый хендл — `consume`-тип с `@cleanup`, поэтому `consume x = … { … }` привязывает
его к блоку, а обращение после закрытия — **ошибка компиляции**, а не
use-after-free. Ни одна экспортированная сигнатура пакета не `unsafe`, и сырой хендл
потребителю не достаётся никогда.

Для тега `sql`…`` из `std/data/sql.nv`:

```nova
import duckdb.sqltag
consume r = con.run(sql`SELECT * FROM sample WHERE percent > ${threshold}`) { … }
```

Значение, переданное так, не становится частью текста запроса — инъекция физически
невозможна.

## Типы

| DuckDB | Nova | примечание |
|---|---|---|
| `BOOLEAN` | `bool` | |
| `TINYINT` … `BIGINT` | `Value.Int(i64)` | |
| `UTINYINT` … `UBIGINT` | `Value.UInt(u64)` | |
| `HUGEINT` | `Value.Huge(i64, u64)` | две половины: ABI для `__int128` не переносим между тремя тулчейнами |
| `FLOAT`, `DOUBLE` | `Value.Real(f64)` | |
| `DECIMAL(p,s)` | `Value.Dec(DecimalValue)` | **никогда не сворачивается в float**, даже для печати |
| `VARCHAR`, `ENUM` | `Value.Text(str)` | |
| `BLOB` | `Value.Bytes([]u8)` | отдельный акцессор от текстового: текстовый *преобразует* значение |
| `TIMESTAMP`, `TIMESTAMPTZ` | `Value.Instant(Timestamp)` | мкс ↔ нс; точность мельче микросекунды **отвергается**, а не срезается |
| `DATE` | `Value.Day(Date)` | |
| `TIME` | `Value.TimeOfDay(Duration)` | от полуночи |
| `INTERVAL` | `Value.Span(Duration)` | интервал с **месяцами** отвергается: месяц не фиксированное число дней |
| `UUID` | `Value.Ident(Uuid)` | 16 байт, без разбора строк |
| `LIST`, `STRUCT`, `MAP`, `ARRAY`, `UNION`, `BIT` | — | `DuckError.Type` с именем колонки |

Два правила стоят отдельно, потому что оба защищают от значения, которое читается
**не таким**, каким записано:

* **`DECIMAL` — не число с плавающей точкой.** Процент в `DECIMAL(5,2)` — точное
  число, которое человек сравнивает с порогом; float — это как 74.00 становится
  73.999999.
* **Момент точнее микросекунды отвергается.** DuckDB считает микросекунды. Срезанная
  запись — другой момент, и построенный по ней график неверен так, что этого не
  видно.

## Сборка

```sh
git submodule update --init --depth 1 native/duckdb
./scripts/build-duckdb.sh            # или: pwsh -File scripts/build-duckdb.ps1        # PowerShell 7; where it is absent:
powershell -ExecutionPolicy Bypass -File scripts\build-duckdb.ps1
nova test src
```

Требуется: **CMake ≥ 3.20, Ninja**, clang (на Windows — clang-cl под `vcvars64`),
8 ГБ RAM. Ожидайте **40–60 минут на 16 ядрах** на холодном кэше; результат
кэшируется меткой по коммиту сабмодуля, флагам и версии компилятора, так что
повторный запуск — no-op.

Собирается репозиторий, а не амальгамация, и именно поэтому это стоит часа:
`core_functions` и `icu` в `libduckdb-src.zip` отсутствуют, а `date_trunc`,
`time_bucket` и арифметика `TIMESTAMPTZ` живут там. При включённой автозагрузке и
отсутствующем расширении первый такой вызов идёт в интернет и висит около двадцати
двух секунд, прежде чем упасть. Шим выключает автозагрузку на соединении, сборка —
в самой библиотеке, поэтому вернуться этот отказ не может.

Добавляет к бинарю около **36 МБ** на каждой платформе.

## Что полезно знать заранее

* **Построчная запись медленная** — около двух миллисекунд на `INSERT`: DuckDB
  колоночный, и это не его путь. Пишите через Appender; `exec` — для точечных
  `UPDATE`.

* **Соединение привязано к потоку.** Все externs помечены `#thread_affine`, поэтому
  вызов из `spawn` — ошибка компиляции, а не гонка, найденная в проде.
* **Слоёв ДВА, и они дают РАЗНЫЕ гарантии.** Эффект `Db` (`db_effect.nv`) —
  мокаемый: девять операций, боевой обработчик поверх DuckDB (`db_real.nv`) и
  любой ваш. Фасад (`Database`/`Connection`/`QueryResult`) зовёт C-шим напрямую и
  никакого обработчика не требует.
* **ЭФФЕКТ ПОКРЫВАЕТ 11 ВЫЗОВОВ ШИМА ИЗ 60, И ЭТО ПРОМЕЖУТОЧНОЕ СОСТОЯНИЕ, А НЕ
  ЗАМЫСЕЛ.** Чтение значений, appender и подготовленные операторы сегодня идут мимо
  эффекта. `Db` этого пакета написан РАНЬШЕ, чем появилась кросс-драйверная граница;
  план 286 её описывает и кладёт чтение строк ВНУТРЬ эффекта (`Rows.@next()`) — то
  есть нынешний срез это то, докуда дошёл пакет, а не то, где он должен остановиться.
  Этап Д5 того плана приводит границу сюда, **не меняя публичного API пакета**; срок
  не назван, потому что у самого этапа есть открытый вопрос.
* **Что из этого следует СЕГОДНЯ, и это надо знать: мок подменяет жизненный цикл и НЕ
  подменяет чтение.** Подмените `query`, потом позовите `value()` — и фальшивая ручка
  уйдёт в настоящий C-вызов. (Форма непокрытых вызовов — как раз то, что D456 п. 3
  запрещает проводить через границу эффекта: `ddb_value_i64(result, row, col)` идёт по
  индексу. Поэтому граница, которая их покроет, — это переделка, а не ещё несколько
  операций того же рода.)
* **Поэтому: чтобы тестировать против подмены, берите ЭФФЕКТ, а не фасад.**
  `Db.describe` и `Db.next` читают строки одной операцией каждая — то, что предписывает
  D456 и что мок может честно обслужить. Фасад предлагает ту же пару
  (`describe`, `next_row`) для прямого употребления.
* **Обработчик требуется во ВРЕМЯ ВЫПОЛНЕНИЯ, а не компиляции.** Вызов операции
  эффекта без `with Db = ...` в области видимости компилируется и падает в рантайме:
  `unhandled effect Db.<op>: no active handler`. Замерено, а не предположено, и верно
  для любого эффекта в этом языке — то есть это обычная форма, а не сюрприз этого
  пакета.
* **Шифрование и `read_only` в 0.1 не реализованы** и **отвергаются**, а не
  игнорируются: настройка безопасности, которая молча ничего не делает, хуже отказа.
